Séance 3 : Introduction aux Design Patterns

Historique des Design Patterns

  • 1977 - Christopher Alexander publie "A Pattern Language" (architecture)
  • 1994 - Gang of Four (GoF) publie "Design Patterns: Elements of Reusable Object-Oriented Software"
  • 23 patterns classifiés dans l'ouvrage original

Classification des 23 Patterns GoF

  • Créationnels (5) : Abstract Factory, Builder, Factory Method, Prototype, Singleton
  • Structurels (7) : Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy
  • Comportementaux (11) : Chain of Responsibility, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor

Ce qu'un pattern N'EST PAS

  • ❌ Ce n'est pas un algorithme - un pattern est une solution de conception, pas une procédure pas-à-pas
  • ❌ Ce n'est pas une bibliothèque - un pattern est une idée, pas du code copier-coller
  • ❌ Ce n'est pas du code prêt à l'emploi - chaque implémentation s'adapte au contexte
  • ❌ Ce n'est pas obligatoire - on ne doit pas forcer un pattern s'il n'est pas nécessaire

Fiche Technique : Iterator

Intention

Permettre un accès séquentiel aux éléments d'un agrégat sans exposer sa représentation interne.

Participants

  • Iterable<T> : interface qui définit la méthode iterator()
  • Iterator<T> : interface qui définit hasNext() et next()
  • Client : code qui utilise le for-each ou l'iterator pour parcourir

Conséquences

  • + Meilleure encapsulation : la structure interne reste cachée
  • + Parcours uniforme : le même code for-each fonctionne pour différentes collections
  • - Une indirection supplémentaire : légère complexité ajoutée

Séance 4 : Principes SOLID

Les 5 Principes SOLID

  • S - Single Responsibility Principle (SRP) : Une classe doit avoir une seule raison de changer
  • O - Open/Closed Principle (OCP) : Ouvert à l'extension, fermé à la modification
  • L - Liskov Substitution Principle (LSP) : Les sous-types doivent être substituables à leurs types de base
  • I - Interface Segregation Principle (ISP) : Les clients ne devraient dépendre que des méthodes qu'ils utilisent
  • D - Dependency Inversion Principle (DIP) : Dépendre des abstractions, pas des implémentations concrètes

Code Smells → Principes Violés

Code Smell Principe Violé Explication
"et" dans la description d'une classe SRP La classe fait plusieurs choses (ex: "format ET écrit ET notifie")
if/switch cascade sur un type OCP Ajouter un nouveau type nécessite de modifier le code existant
UnsupportedOperationException dans une implémentation ISP L'interface est trop grosse, certaines méthodes ne s'appliquent pas
new d'un détail technique dans la logique métier DIP Le code dépend directement d'une implémentation concrète

Rétrospective SOLID sur les Sessions Précédentes

  • Session 1 : Revue n'implémente pas Empruntable → ISP (Revue ne dépend pas de méthodes qu'elle ne peut pas utiliser)
  • Session 2 : Bibliothecaire HAS-A Catalogue → DIP (dépendance sur l'abstraction, pas sur l'implémentation concrète)
  • Session 3 : Catalogue implémente Iterable → OCP (ouvert à différents parcours, fermé à la modification de la structure interne)

Application SOLID : RapportService

SRP - Séparation des Responsabilités

  • FormatRapport : charge de formater (CSV, TXT, JSON)
  • DestinationRapport : charge d'écrire (disque, mémoire, etc.)
  • Notificateur : charge de notifier (email, SMS, etc.)
  • RapportService : orchestration uniquement

OCP - Format Extensible

Ajouter FormatJson ne nécessite AUCUNE modification des fichiers existants. Seul un nouveau fichier est créé.

Preuve : FormatJson a été ajouté sans toucher à RapportService, FormatCsv, FormatTxt, ou les tests existants.

DIP - Injection de Dépendances

  • RapportService reçoit FormatRapport, DestinationRapport, Notificateur via constructeur
  • Pas de new FileWriter, new ServeurSmtp dans la logique métier
  • Les implémentations concrètes (EcrivainDisque, NotificateurEmail) sont injectées
  • Les exceptions ne sont plus avalées (IOException propagée)

Testabilité - Fakes/Stubs

Grâce au DIP, RapportService est testable sans :

  • Toucher au système de fichiers réel (FakeDestination écrit en mémoire)
  • Envoyer de vrais emails (FakeNotificateur enregistre juste l'appel)
  • Utiliser des formats complexes (FormatCsv est simple et testable)
